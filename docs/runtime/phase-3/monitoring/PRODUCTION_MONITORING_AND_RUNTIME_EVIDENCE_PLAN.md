# PRODUCTION_MONITORING_AND_RUNTIME_EVIDENCE_PLAN

## 1. Purpose

`PRODUCTION_MONITORING_AND_RUNTIME_EVIDENCE_PLAN` is the first operational evidence plan after Phase 2.6.

This is a planning artifact only.

It does not modify runtime, agents, Strategy, Publisher, Orchestrator, QC, Experiment, Attribution, or the core pipeline.

The purpose is to define how real runtime evidence will be collected before Phase 3 is allowed to close residuals, change operational behavior, or open any candidate agent hardening/reopen work.

Final principle:

> Phase 3 does not improve the system by assumption. It earns improvement rights through runtime evidence.

## 3. Evidence Principles

Production evidence must be:

- real
- timestamped
- attributable to a run, artifact, or publish attempt
- append-only where practical
- explicit about missing data
- explicit about fallback
- explicit about degraded inputs
- separable from assumptions
- serializable
- auditable

Production evidence must not:

- invent runtime events
- infer publish success without publish evidence
- treat fallback as success
- treat post-publish metrics as causal proof without attribution rules
- close residuals without enough runtime history
- silently hide failures or skipped stages
- mutate agent behavior while collecting evidence

## 4. Evidence Sources

Primary evidence sources:

- creative orchestrator run records
- agent result artifacts
- Strategy decision traces
- Account Health decisions
- Script/Voice/Asset/QC traces
- render artifacts
- publish lifecycle events
- publish records
- post-publish metrics
- attribution outputs
- experiment assignment records
- incident records
- residual monitoring ledger

Source classification:

```json
{
  "runtime_trace": "direct evidence from execution",
  "artifact_metadata": "evidence from generated artifacts or manifests",
  "publish_lifecycle": "evidence from publish attempt/result flow",
  "post_publish_metrics": "delayed outcome evidence",
  "manual_observation": "human-entered evidence requiring explicit label",
  "fallback_or_missing": "evidence gap, not success"
}
```

Evidence priority:

1. direct runtime trace
2. generated artifact metadata
3. publish lifecycle event
4. post-publish metric window
5. governed manual observation
6. fallback/missing evidence marker

## 5. Runtime Event Model

Runtime events should be appended to:

- `OUT/runtime_evidence/production_runs.jsonl`

Recommended event shape:

```json
{
  "event_id": "string",
  "run_id": "string",
  "timestamp": "ISO-8601",
  "event_type": "RUN_STARTED | AGENT_COMPLETED | AGENT_FAILED | FALLBACK_USED | ARTIFACT_CREATED | RUN_COMPLETED | RUN_FAILED",
  "agent": "strategy | account_health | learning | trend | script | voice | asset_selection | editor | video_qc | publisher | attribution | experiment | orchestrator",
  "status": "success | failed | skipped | degraded | fallback",
  "input_refs": [],
  "output_refs": [],
  "trace_refs": [],
  "fallback_used": false,
  "degraded_inputs": [],
  "missing_inputs": [],
  "boundary_statement": "string",
  "metadata": {}
}
```

Required runtime event rules:

- every production run must have a `RUN_STARTED`
- every production run must have `RUN_COMPLETED` or `RUN_FAILED`
- every skipped stage must have a reason
- every fallback must be explicit
- missing trace is evidence gap, not success
- event IDs must be deterministic where derived from available stable values, otherwise generated by the runtime event writer and persisted

This plan defines the schema only. It does not implement the event writer.

## 6. Publish Lifecycle Evidence

Publish lifecycle evidence should be appended to:

- `OUT/runtime_evidence/publish_lifecycle.jsonl`

Recommended event shape:

```json
{
  "publish_event_id": "string",
  "run_id": "string",
  "content_id": "string",
  "timestamp": "ISO-8601",
  "event_type": "PUBLISH_ELIGIBILITY_CHECKED | PUBLISH_ATTEMPTED | PUBLISH_SUCCEEDED | PUBLISH_FAILED | PUBLISH_SKIPPED",
  "publisher_authority_invoked": true,
  "qc_status": "APPROVE | HOLD | REJECT | UNKNOWN",
  "qc_publishable": true,
  "account_health_decision": "SAFE | CAUTION | HOLD | UNKNOWN",
  "strategy_ref": "string",
  "artifact_refs": [],
  "publish_target": "string",
  "skip_reason": "string | null",
  "failure_reason": "string | null",
  "fallback_used": false,
  "boundary_statement": "Publisher is explicit publish authority; QC evaluates final artifact.",
  "metadata": {}
}
```

Required publish rules:

- Publisher must be explicit publish authority.
- QC must not publish.
- Publisher must not override Account Health HOLD.
- Publisher must not hide failed or skipped attempts.
- Publish success requires explicit `PUBLISH_SUCCEEDED`.
- Missing publish evidence must not be inferred as success.

## 7. Post-Publish Metrics Windows

Post-publish metrics should be appended to:

- `OUT/runtime_evidence/post_publish_metrics.jsonl`

Recommended metric windows:

- `1h`
- `6h`
- `12h`
- `24h`
- `72h`
- `7d`

Recommended event shape:

```json
{
  "metric_event_id": "string",
  "content_id": "string",
  "publish_event_id": "string",
  "window": "1h | 6h | 12h | 24h | 72h | 7d",
  "window_started_at": "ISO-8601",
  "window_ended_at": "ISO-8601",
  "metrics_available": true,
  "metrics": {
    "views": 0,
    "retention": null,
    "completion_rate": null,
    "likes": 0,
    "comments": 0,
    "shares": 0,
    "saves": 0,
    "negative_feedback": 0
  },
  "missing_metrics": [],
  "metric_source": "string",
  "collection_status": "complete | partial | missing | delayed",
  "attribution_ready": false,
  "rationale": "string"
}
```

Rules:

- early windows are weak evidence
- delayed/missing metrics must remain explicit
- metric availability does not imply causality
- attribution readiness requires sufficient window completion
- no Learning/Strategy update should treat partial metrics as strong evidence

## 9. Evidence Confidence Levels

Evidence confidence levels:

```json
{
  "none": "no evidence available",
  "weak": "single controlled or partial runtime signal",
  "moderate": "multiple runtime signals or complete short window evidence",
  "strong": "repeated runtime evidence across contexts and completed metric windows",
  "operational": "sustained production evidence with incident review and attribution support"
}
```

Rules:

- fallback-only evidence cannot exceed `weak`
- missing post-publish windows cannot exceed `moderate`
- causal claims require attribution support
- operational confidence requires time, repeated runs and incident review
- confidence must describe evidence quality, not expected performance

- no optimization is authorized merely because a stage completed

## 12. Anti-Fake-Causality Rules

Forbidden:

- claiming a script caused performance without attribution support
- claiming a trend caused performance from a single publish
- treating correlation as causation
- treating early metrics as final outcome
- ignoring account health, timing, platform effects or experiment exposure
- allowing Learning to strengthen policy from contaminated or partial evidence
- allowing Strategy to change because of weak attribution evidence

Required:

- causal strength classification
- metric window completeness
- attribution confidence
- contamination handling
- delayed metric handling
- explicit uncertainty

Attribution levels:

```json
{
  "none": "no attribution evidence",
  "weak": "correlation or incomplete window only",
  "moderate": "repeated pattern with controls or sufficient context",
  "strong": "validated repeated signal with contamination controls",
  "not_claimed": "system explicitly declines causal interpretation"
}
```

## 13. Residual Closure Rules

Residual closure requires:

- residual exists in ledger
- residual source is known
- minimum run count is met
- required metric windows are complete where applicable
- incidents are reviewed
- evidence confidence is at least the required level
- closure rationale is written
- closure is validated by a gate or review artifact

Residuals must not close when:

- evidence is controlled-only but residual requires production
- evidence is fallback-only
- incidents remain unresolved
- metric windows are incomplete
- attribution is weak but causal reduction is claimed
- boundary risk is present

## 14. Failure Conditions

This plan fails if future implementation:

- changes runtime behavior before evidence collection is defined
- starts Publisher work without publish evidence schema
- starts Strategy/Novelty/Editor hardening without governance reopen evidence
- closes residuals without runtime evidence
- hides fallback
- hides failed publish attempts
- treats missing metrics as success
- creates fake causality
- lets QC become Publisher
- changes core pipeline without formal reopen

## 15. Exit Criteria

This plan is complete when the system has:

- defined runtime evidence schemas
- defined publish lifecycle evidence
- defined post-publish metric windows
- defined residual monitoring ledger
- defined evidence confidence levels
- defined incident classification
- defined rollout stages
- defined anti-fake-causality rules
- defined residual closure rules
- preserved all Phase 2.6 boundaries

It does not require runtime implementation.
