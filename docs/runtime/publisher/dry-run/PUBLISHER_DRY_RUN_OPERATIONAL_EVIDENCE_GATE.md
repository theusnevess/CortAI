# PUBLISHER_DRY_RUN_OPERATIONAL_EVIDENCE_GATE

## 1. Purpose

`PUBLISHER_DRY_RUN_OPERATIONAL_EVIDENCE_GATE` is the formal future gate specification for Publisher dry-run operational evidence.

This is a gate specification only.

It must not create a runner, execute tests, modify runtime, call platform APIs, upload content, schedule publication, collect post-publish metrics, make attribution causal claims, or change Strategy, QC, Account Health, Orchestrator, Attribution, Experiment or core pipeline behavior.

The gate validates operational evidence generated by Publisher trace-only dry-run execution.

It proves observability in volume, not real publication.

Final principle:

> Dry-run evidence may prove Publisher trace observability. It must not pretend to prove real platform publishing or post-publish outcomes.

## 2. Scope

In scope:

- dry-run lifecycle evidence
- `OUT/runtime_evidence/publish_lifecycle.jsonl`
- coverage minimums
- state distribution
- temporal consistency
- append-only validation

- no platform side effects

Out of scope:

- real publishing
- platform API calls
- upload
- scheduling

- real platform content ID
- post-publish metrics
- attribution causality
- performance prediction
- Strategy changes

## 4. Minimum Coverage Requirements

The future gate must validate minimum dry-run evidence coverage.

Initial required thresholds:

```json
{
  "minimum_evidence_requirements": {
    "min_total_runs": 50,
    "min_qc_blocks": 5,
    "min_account_health_hold_blocks": 3,
    "min_missing_qc_trace_events": 2,
    "min_missing_artifact_manifest_events": 2,
    "min_incident_hooks": 5,
    "min_append_only_events": 50
  }
}
```

Thresholds may be adjusted by explicit governance update.

They must not be omitted by the runner.

The runner must fail or return `HOLD` if it cannot compute coverage.

Coverage must be based on evidence records, not assumptions.

## 5. State Distribution Requirements

The gate must prevent a dry-run batch that always appears healthy.

Required state constraints:

```json
{
  "state_distribution_requirements": {
    "eligible_count_gt_zero": true,
    "blocked_count_gt_zero": true,
    "skipped_count_gt_zero": true,
    "qc_block_count_gt_zero": true,
    "account_health_hold_block_count_gt_zero": true,
    "success_count_equals_zero": true,
    "fake_success_detected": false,
    "eligible_ratio_max": 0.8,
    "skipped_ratio_min": 0.1,
    "blocked_ratio_min": 0.1
  }
}
```

Dry-run evidence is insufficient if:

- every run is eligible
- no run is blocked
- no run is skipped
- no QC block appears
- no Account Health `HOLD` block appears
- any dry-run success appears

## 6. Temporal Consistency Requirements

The gate must validate temporal consistency across lifecycle evidence.

Required checks:

- timestamps parse as ISO-8601 or accepted runtime timestamp format
- events are orderable
- no event timestamp predates the logical `RUN_STARTED` event for that run, when present
- no time travel within a run
- `run_id` is coherent between eligibility, attempt and result
- `content_id` is coherent between eligibility, attempt and result
- lifecycle transitions are valid

Valid dry-run lifecycle transitions:

- eligibility checked -> skipped
- eligibility checked -> not attempted
- eligibility checked -> attempted -> failed
- eligibility checked -> attempted -> pending

Invalid dry-run lifecycle transitions:

- eligibility checked -> succeeded
- skipped -> succeeded
- failed -> succeeded
- pending -> succeeded
- any transition with URL or platform content ID

Temporal inconsistency is a blocking failure.

## 7. Append-Only Requirements

The gate must validate append-only behavior for `publish_lifecycle.jsonl`.

Required checks:

- JSONL preserves existing lines
- new dry-run executions only add lines
- no prior event is rewritten
- no prior event is deleted
- failures remain failures
- skips remain skips
- pending remains pending
- no prior event is converted into success
- append-only event count meets `min_append_only_events`
- every appended line is valid JSON
- every appended event has a stable `publish_event_id`

The future runner should compare file state before and after dry-run evidence generation.

An append-only violation is a blocking failure.

## 8. Fake Success Prevention

The gate must fail if any dry-run event includes:

- `result_status = succeeded`
- non-null `published_url`
- non-null `platform_content_id`
- `result_evidence_available = true`
- platform receipt
- upload ID
- scheduler ID
- real publish target success

The gate must also fail if:

- eligibility is counted as success
- pending is counted as success
- skipped is counted as success
- absence of failure is counted as success

Dry-run success count must be exactly zero.

## 9. Residual Monitoring Rules

The gate must keep these production residuals open:

- `PRODUCTION_PUBLISH_EVIDENCE_NOT_AVAILABLE_YET`
- `PLATFORM_INTEGRATION_NOT_ENABLED`
- `PUBLISH_RESULT_HISTORY_STILL_SHORT`

Dry-run may reduce only observability residuals, such as:

- dry-run lifecycle trace coverage
- incident hook coverage
- skip/failure visibility coverage
- append-only confidence

Dry-run must not close:

- production publish evidence residuals
- platform integration residuals
- post-publish metric residuals
- attribution causality residuals

Closing production residuals with dry-run evidence is a blocking failure.

The runner may generate controlled dry-run evidence or validate pre-existing dry-run evidence, but it must label which mode was used.

Synthetic-only evidence must not be mislabeled as production evidence.

## 12. Verdict Semantics

Allowed verdicts:

- `GO`
- `GO_WITH_MONITORING`
- `HOLD`

`HOLD` if:

- minimum coverage is not met
- state distribution is always healthy
- dry-run success appears
- URL or platform content ID appears
- result evidence appears in dry-run as real publish proof
- append-only is violated
- temporal consistency fails
- time travel is detected
- production residual is closed
- platform API is called
- upload occurs
- scheduler is invoked
- real publishing is performed
- boundary violation occurs
- fake causality appears
- silent failure is detected

`GO_WITH_MONITORING` if:

- all critical checks pass
- dry-run evidence coverage is sufficient
- distribution is realistic enough for observability
- temporal consistency holds
- append-only holds
- production residuals remain open
- real publishing still does not exist

`GO` only if a future governance context explicitly authorizes production evidence and real production evidence exists.

For this dry-run gate, expected likely result is:

- `GO_WITH_MONITORING`

The future runner must derive the verdict from evidence and must not hardcode it.
